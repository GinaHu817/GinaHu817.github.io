LoRA: Teaching a Giant Model a New Trick Without Moving All Its Weights

Two small matrices, one frozen model, and a surprisingly big idea. I followed LoRA's future-work questions into 2026 to see which ones grew up, and which still deserve an experiment.
November 2026  ·  14 min read

In my BERT post, fine-tuning meant updating the reader itself. That sounds perfectly reasonable until the reader has billions of parameters and you want a different version for every task. Suddenly, “just fine-tune it” starts sounding like “just buy another GPU.” Very helpful, thank you.

LoRA: Low-Rank Adaptation of Large Language Models, by Edward J. Hu and colleagues, asks whether adapting a model really requires changing that many independent things. The paper first appeared in 2021 and was published at ICLR 2022. Its central move is wonderfully economical: freeze the existing weights and learn a small, structured correction. (Original paper.)

What grabbed me in my notes wasn't just the memory saving. It was the possibility that a model can know an enormous amount while needing only a few new directions to use that knowledge differently.

The Model Is Huge. Does the Change Have to Be?

Picture a giant mixing desk. Pre-training has already set thousands of controls to produce a useful sound. A downstream task might need a different balance, without requiring every control to move independently. LoRA bets that a small number of coordinated adjustments can often do the job.

That is an intuition about the change, not a claim that the whole model is simple. My notes connect it to research on low intrinsic dimensionality: useful solutions may be reachable inside a much smaller space than the raw parameter count suggests. LoRA turns that motivation into a concrete constraint on weight updates.

Rank, without the ceremonyA matrix's rank counts its independent directions. A rank-8 update can coordinate changes across thousands of input and output coordinates, but those changes must pass through at most eight independent intermediate directions.

Low intrinsic dimension and low matrix rank are related motivations, not interchangeable mathematical statements. LoRA's low-rank design is a hypothesis we can test. It doesn't follow automatically from the model having a useful small subspace.

The Entire Trick Fits in One Equation

Take a weight matrix W₀ with d_out rows and d_in columns. Ordinary fine-tuning can learn an unrestricted change to that matrix. LoRA instead learns two smaller matrices:

A: r × d_in    B: d_out × r
ΔW = (α / r) BA
h = W₀x + (α / r) B(Ax)

A maps the input into an r-dimensional space; B maps it back to the output size. The product has rank at most r. The factor α/r controls the update's scale; when writing W′ = W₀ + BA, we're simply leaving that scale implicit.

Base path: x → W₀ → W₀xKeep the pre-trained weight matrix frozen.
Update path: x → A → B → scaled BAxTrain these two small matrices for the downstream task.
Add the two outputs → the adapted layer's output, h

There is no activation function between A and B in this update. That linear structure matters: it lets us fold the correction into the original weight later. The paper initializes A randomly and B to zero, so training starts with a zero correction and the base model's original behavior. (Section 4.1.)

A small calculation made the saving click for me

For one square 4,096 × 4,096 matrix, full fine-tuning trains 16,777,216 parameters. With r = 8, LoRA trains 8 × 4,096 + 4,096 × 8 = 65,536. That's 256 times fewer trainable parameters for this matrix. The original 16.8 million weights still exist; we just aren't optimizing them.

The general count is r(d_in + d_out) per adapted matrix. For M square matrices of width d, it becomes 2Mdr. Here M counts matrices, not Transformer blocks: adapting query and value in every block gives two adapted matrices per block.

A detail I want to keep straight: fewer trainable parameters does not mean the same reduction in total VRAM or training time. We still run the base model, and gradients still need to travel through its computation to reach the adapters. We save the frozen weights' gradients and optimizer state, not the entire cost of using them.

Why Not Add Adapters or Tune the Prompt?

My notes compare two other routes: add task-specific modules, or learn continuous prompt/prefix vectors while keeping the main model fixed. These are useful alternatives with different costs.

Three ways to adapt a frozen model
MethodWhat learnsWhat to watch
Bottleneck adaptersSmall inserted networks, usually down-project → activation → up-project.Sequential adapter computation can add inference latency.
Prompt / prefix tuningContinuous vectors that steer the model through its input or attention context.Virtual positions add attention work and can consume the available sequence budget, depending on implementation.
LoRAA low-rank correction to selected existing weight matrices.A fixed correction can be merged into the base weight; live adapter switching has different serving costs.

An adapter with input/output width d and bottleneck width b has 2db + b + d parameters if both projections include biases. That looks similar to LoRA's 2dr, but a similar parameter count doesn't make the computation identical. The adapter's nonlinearity prevents the same simple weight merge.

For merged LoRA, inference just uses W_merged = W₀ + (α/r)BA. Same matrix shape, same kind of matrix multiplication. This is the specific condition behind the paper's no-added-latency claim. Keeping multiple unmerged adapters available for different requests can require additional kernels and routing. Quantized deployment also needs care when merging and re-quantizing.

The original GPT-3 experiments reported roughly a threefold reduction in training memory and around a 25% training speedup relative to their full fine-tuning setup. Those are results for that configuration, not a promise about every model or GPU. (Section 4.2.)

Where Do You Put Those Two Matrices?

The original study mainly adapts attention projections, leaving the feed-forward MLP frozen. Queries and keys determine attention scores; values supply the information being combined. Changing different projections gives the model different ways to adapt.

I had written “query + value works best” in my notes. The more useful lesson is about the budget. In the paper's GPT-3 comparison, spreading a fixed number of parameters across query and value is stronger than putting them all into either one alone. But adapting all four attention projections ties query + value on WikiSQL and scores higher on MultiNLI. So this isn't a universal decree that keys and output projections don't matter. (Table 5.)

Likewise, very small ranks can work competitively in the experiments without being sufficient for every task. The top singular directions learned at ranks 8 and 64 overlap substantially; weaker directions overlap less. My reading is that increasing capacity sometimes gives you more variations around the same important adjustment, rather than a completely new useful skill.

The paper also finds that the correction can amplify directions that are present but relatively weak in the pre-trained weights. The mixing-desk analogy becomes tempting here: turn up a useful channel. But that is an interpretation of spectral evidence, not proof that each singular vector corresponds to a human-readable concept. (Sections 7.2 and 7.3.)

“Just Combine the Adapters” Has a Catch

One question in my notes is especially practical. Suppose one adapter learns SQL and another learns a writing style. Which one should answer a request for an SQL explanation in that style?

We can add their weight updates, but addition doesn't guarantee that their behaviors will cooperate. Even the algebra deserves a second look:

Desired sum: B₁A₁ + B₂A₂
(B₁ + B₂)(A₁ + A₂)
= B₁A₁ + B₂A₂ + B₁A₂ + B₂A₁

Adding the factors creates extra cross terms. Concatenating factors can represent the exact sum, but its rank budget can grow to r₁ + r₂. And even an exact sum of updates can produce unwanted interactions once it passes through the rest of a nonlinear network. “Two adapters fit in memory” and “two skills compose correctly” are different achievements.

This question has already inspired research. LoraHub explores composing previously trained LoRA modules for new tasks with a few examples. That is a useful starting point, not evidence that arbitrary adapters can be mixed safely or that an unseen combination will work without evaluation.

LoRA's Future Work, Revisited in November 2026

The original paper ends with four directions; its methods section also leaves MLPs, LayerNorm, and biases for later. I followed all five threads. The status below means there is concrete follow-up work, not that the whole problem is solved. The proposed experiments are my reading of worthwhile next steps, not claims that nobody has attempted related work.

1. Go beyond the attention projections

Explored: MLPs, biases, and normalization all have evidence.

QLoRA (2023) finds that adapting all linear Transformer-block layers, including the MLP, is important for matching full fine-tuning in its LLaMA-7B/Alpaca comparison. BitFit, contemporary work first released in 2021 and published at ACL 2022, studies bias-only tuning of BERT. Tuning LayerNorm in Attention (2023 preprint; ICLR 2024) studies normalization tuning for multimodal adaptation. These address the broader parameter-choice question; bias and LayerNorm tuning aren't themselves low-rank matrix updates.

What I'd still explore: under a fixed GPU-hour budget, when should a newer model spend its adaptation capacity on attention, MLPs, or normalization? I'd compare attention-only LoRA, all-linear LoRA, and LoRA plus normalization tuning, while measuring both task quality and retention of general abilities. A result on BERT or a particular multimodal setup doesn't settle that choice for every architecture.

2. Combine LoRA with other efficient methods

Demonstrated: combinations exist; their benefits depend on the setup.

This wasn't entirely left for the future: LoRA's own Appendix E already tests a combination with prefix tuning. UniPELT (ACL 2022) combines LoRA, prefix tuning, and adapters with learned gates. QLoRA pairs low-rank training with a frozen 4-bit base model, reducing the memory occupied by the base weights as well.

What I'd still explore: which combination gives the best quality at the deployment latency you can actually afford? I'd hold the data and training budget fixed, then compare merged LoRA, a gated hybrid, and quantized LoRA on the same workload. A hybrid that wins on trainable parameter count can still lose on response time. The appealing target is complementary improvements that survive an end-to-end measurement.

3. Understand what fine-tuning actually changes

Partly explained: stronger empirical and theoretical tools, no universal account.

LoRA vs Full Fine-tuning: An Illusion of Equivalence (2024 preprint; NeurIPS 2025) identifies new prominent singular directions, called intruder dimensions, in LoRA-adapted weights. Its interventions connect those directions to forgetting in the tested settings. Matching downstream accuracy can therefore hide different internal changes.

For a fresh 2026 perspective, Zindari, Mulayoff, and Stich's May preprint analyzes LoRA versus full fine-tuning in linear regression. It identifies regimes where low-rank task differences favor LoRA's generalization. That's a precise explanation under a simplified model, with supporting practical experiments, rather than a theorem covering every Transformer.

What I'd still explore: can we predict harmful forgetting before deployment? I'd track spectral changes through training, intervene on suspicious directions, and check whether those interventions preserve both the new task and older capabilities. The test should include sequential adaptation, where today's useful correction can become tomorrow's interference.

4. Choose matrices and ranks more systematically

Active research: adaptive allocation exists, and 2026 work connects rank to data.

AdaLoRA (2023) allocates a parameter budget across weight matrices using importance scores, rather than assigning every matrix the same rank. This is a concrete answer to part of the placement-and-budget question, though it remains an adaptive scoring method rather than a universal optimality guarantee.

An October 2026 preprint, A Fine-Grained Analysis of the LoRA Fine-Tuning Landscape with Implications for Data Selection, links sufficient rank to data-dependent optimization geometry through a condition called LoRA-RIP. Its theory treats a single adapted matrix under explicit assumptions; its limitations section leaves joint multi-layer theory and larger generative fine-tuning for further study.

What I'd still explore: choose the training examples and rank allocation together. I'd compare uniform ranks, AdaLoRA, and a data-aware allocation at equal total cost, including the cost of selecting data. Better data coverage might make a smaller adapter work better, but I would want that demonstrated on long-form generation before treating it as a general recipe.

5. Is the original weight matrix compressible too?

Explored as compression research; low-rank updates alone don't establish it.

This is where I had to correct my notes. A low-rank ΔW does not imply a low-rank W₀. An identity matrix has full rank; adding a rank-1 correction doesn't turn that fact into evidence of redundancy. Adaptation asks how many directions need to change. Compression asks how much of the existing computation we can remove.

SVD-LLM (2024) and SVD-LLM V2 (2025) study low-rank compression of LLM weights while accounting for the effect of truncation on model behavior. Their existence supports pursuing compression, not concluding that every pre-trained matrix is exactly rank-deficient.

What I'd still explore: allocate compression rank and adaptation rank jointly. I'd compare compress-then-adapt against adapt-then-compress, measuring quality, peak memory, and actual inference latency. The two ranks solve different problems, so forcing them to share one budget rule seems like a question to investigate rather than an obvious shortcut.

The experiment I'd start with: a fixed-budget study of data coverage and rank allocation, followed by a forgetting check. It connects the 2026 theory to a decision a small lab actually faces: should the next GPU hour buy a larger adapter, a better selection of examples, or a different set of adapted layers?

Cheat Sheet: The Distinctions I Want to Keep

Low-rank update vs. low-rank modelLoRA constrains the correction. The frozen base matrix can still have full rank, and its storage doesn't disappear.
Rank vs. where you adaptIncreasing rank gives one update more capacity. Adapting another matrix gives the model a different place to change. Compare them under an explicit budget.
Parameter efficiency vs. system efficiencyCount trainable weights, but also measure activations, optimizer state, training time, and serving latency.
LoRA vs. COMPACTERCOMPACTER (2021) makes adapter layers compact using sums of Kronecker products with shared components and low-rank task-specific factors. It is related structured parameterization, with a different adapter architecture.

What I'm Taking Away

  • A huge pre-trained model can sometimes adapt through a small number of coordinated weight changes.
  • LoRA's practical elegance comes from training small factors and merging a fixed linear correction for inference.
  • MLP adaptation, hybrid tuning, adaptive rank allocation, and weight compression have all been explored.
  • The questions still worth testing concern when those methods work, how they interact, and what they preserve.

I started with “how do we avoid updating billions of weights?” I ended up with “which changes does this task actually need?” That feels like the deeper gift of LoRA: it makes an expensive adaptation problem small enough to inspect, challenge, and experiment with.
